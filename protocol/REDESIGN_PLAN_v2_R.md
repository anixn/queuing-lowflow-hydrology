## 2. Design principles (the rules the new code must enforce)

1. **One claim unit per gauge, derived from that gauge.** A claim is 20 mm of water
   over the gauge's own command area. Demand and supply are first computed in
   mm/day over the same area, then divided by the same claim depth. Area cancels
   in demand; it enters supply exactly once. No cross-gauge constants (kills F1).
2. **Catchment-relative thresholds.** q*, K, theta, and the service cap are
   formulas of each gauge's own mean demand rate, not constants (kills U1, U2, U5).
3. **Utilization before inference.** No gauge enters the comparison until its
   utilization rho = mean(lambda)/mean(mu) is computed and inside the predeclared
   window; the rho distribution of ALL screened gauges is reported either way
   (kills F3's root cause and makes the "queue is far from congestion" question
   answerable with evidence).
4. **Deliverable supply, not river discharge.** Supply is min(firm flow share,
   infrastructure delivery cap in mm/day) with the cap chosen so it can actually
   bind (kills U7).
5. **Demand with documented provenance and bounds.** Stage A (envelope) and
   Stage B (measured/estimated irrigation demand) both defined; the paper reports
   which stage every number came from (kills U6).
6. **Zeros are a data-quality question, not a modeling assumption.** A dedicated
   audit stage classifies every zero against an independent record; three
   predeclared treatment variants run end to end (kills F2).
7. **Power before testing.** A pre-study power calculation decides the gauge count
   and whether the confirmatory framing is allowed at all (kills F4, U8).
8. **Two endpoints: diagnostic AND prospective.** The prospective 1-month-lead
   test is where the queue's persistence can genuinely add information (kills U3,
   addresses F5).
9. **Leakage-clean primary target.** The primary target's climatology uses
   training years only; externally standardized benchmarks are kept but labelled
   exploratory (kills U4).
10. **No silent interpolation.** Gap table first, explicit rule, flag columns,
    month-exclusion rule for long gaps (kills the F6 interpolation error class).
11. **Exactness culture retained.** The engine keeps exact stationary solutions,
    RK4 transient, thinning DES cross-check, conservation ledger, first-passage —
    now in R with a standalone verification battery (preserves what worked).
12. **Provenance sidecars.** Every generated CSV gets a companion `.json` with
    script name, git hash, parameters, seed, sessionInfo (kills F8's class).

## 3. Scientific redesign

### 3.1 Unit system (fixes F1, U1, U2)

For gauge g with command area `A_cmd[g]` (m^2) and claim depth `d = 20 mm`:

- Claim volume: `V_claim[g] = d/1000 * A_cmd[g]` (m^3). One per gauge. Used for
  BOTH demand and supply. Nothing else defines a claim anywhere in the codebase.
- Demand: `need_mm(t) = max(Kc(doy) * PET0(t) - phi * P(t), 0)` in mm/day over the
  command area. In claims: `lambda(t) = need_mm(t) / d` (claims/day). Area
  cancels — lambda is a depth rate, which is exactly why it was gauge-independent
  before; the gauge dependence now enters through supply and through the
  catchment-relative thresholds, not through a duplicated area constant.
- Supply: raw firm abstraction
  `S_raw(t) = Q(t) * 86400 * s_firm` (m^3/day; Q in m^3/s times 86,400 s/day —
  no other factor),
  expressed over the command area: `S_mm(t) = S_raw(t) / A_cmd[g] * 1000` (mm/day),
  capped by infrastructure: `mu(t) = min(S_mm(t), cap_mm) / d` (claims/day),
  with `cap_mm = 10` mm/day default (canal application rates are typically 5–15
  mm/day; the old 60 mm/day cap could never bind — this one can).
- Assertions enforced in code: `lambda` and `mu` for gauge g must carry the same
  `V_claim[g]`; a unit-consistency test recomputes both from raw inputs and fails
  on any mismatch; the command area appears exactly once in the supply path.

`A_cmd[g]` is documented per gauge with its source and uncertainty (§3.2, §S3).
A worked check (mandated as a test): with `A_cmd = 45,000 ha`, `d = 20 mm`,
`s_firm = 0.5`, `Q = 500 m^3/s`: `S_mm = 0.5*500*86400/4.5e8*1000 = 48 mm/day`,
capped at 10 mm/day → `mu = 0.5 claims/day`; with need 2 mm/day → `lambda = 0.1`,
so `rho = 0.2` — in the interesting window. The old pipeline's unconstrained
48 mm/day supply was ~24x demand, which is exactly why the queue never filled.

### 3.2 Demand model — two stages, both predeclared

**Stage A (demand envelope, always run).** Crop-water deficit of the command area:

- `Kc(doy)`: kharif season from `sowing_doy = 200`, length 120 d,
  `Kc = 0.4 + 0.8 * sin(pi * phase)` for phase in [0,1], else 0.35 (unchanged,
  now a named function with documentation).
- `PET0`: Hargreaves from CAMELS-IND tmax/tmin **or** GLEAM PET as before — one
  source per run, recorded. (If Hargreaves is computed anywhere, the extraterrestrial
  radiation MUST be converted MJ m^-2 day^-1 → mm/day with the factor 0.408 before
  entering FAO-56 Eq. 21; this was the 2.45x error in the old `03_extract_cmip6.R`.
  A verification test reproduces a tabulated FAO-56 example value.)
- `phi = 0.7` effective rainfall fraction (documented assumption).
- `A_cmd[g]` Stage A default: irrigated area inside the catchment estimated from
  district irrigation statistics (India-WRIS / CGWB district profiles, which the
  repository already holds for Sangli and Yadgir) cropped to catchment overlap;
  when district data are unavailable, `A_cmd = f_irr * A_catchment` with
  `f_irr = 0.10` and a predeclared bounds sweep `f_irr in {0.03, 0.10, 0.25}`.
  Every choice recorded in the catchment table with source and year.

**Stage B (measured/estimated demand, the headline upgrade).** For each selected
gauge, build a monthly irrigation demand series from canal-command data: commanded
area x cropping calendar x crop water requirement, cross-checked against reported
canal releases where obtainable. Stage B demand replaces the Kc-curve synthetic
demand for the primary sensitivity contrast. If Stage B data cannot be obtained
for a gauge, that gauge runs Stage A only and is flagged; the protocol reports
how many gauges are Stage A vs Stage B (this is a limitation statement, not a
hidden variable).

Both stages produce the same output schema (daily `need_mm`, `lambda` claims/day),
so downstream code is stage-agnostic.

### 3.3 Supply model — three predeclared variants

- `SUP-1` (baseline): `s_firm = 0.5` share of observed flow, capped at 10 mm/day.
- `SUP-2` (firm-yield): dependable flow = min of daily flow and the gauge's Q95
  (flow exceeded 95% of the time), replacing the proportional share
  (`s_firm` = 1 within SUP-2): `S_mm(t) = min(Q(t), Q95_ref) * 86400 / A_cmd * 1000`, same cap. Represents "dependable supply" hydrology.
- `SUP-3` (infrastructure-first): supply = cap whenever Q(t) >= Q_eco (ecological
  floor = 10% mean flow), else proportional share, capped. Represents a canal
  system with a minimum environmental release.
All three run for every gauge; SUP-1 is the primary, SUP-2/SUP-3 are predeclared
sensitivities. The intake cap `cap_mm in {5, 10, 20}` is a predeclared sweep —
unlike the old fixed 60 mm/day that never bound.

### 3.4 Catchment-relative queue parameters (fixes U2)

All threshold-like quantities are formulas of the gauge's own mean demand rate
`lam_bar[g] = mean(lambda)` over the analysis period (claims/day):

| Parameter | Formula | Default | Meaning |
|---|---|---|---|
| `q*` | `ceiling(q_days * lam_bar)` | q_days = 60 | critical backlog = 2 months of mean unmet demand |
| `K` | `min(80, max(25, ceiling(K_days * lam_bar)))` | K_days = 365 | capacity = 1 year of demand |
| `theta` | `ceiling(1.5 * q*)` | — | emergency-service onset |
| `alpha` | constant | 1.5 | boost multiplier above theta |
| `eta` | constant | 1/60 per day | reneging: mean waiting tolerance ~60 days |
| `cap_mm` | constant (mm/day) | 10 | delivery cap (§3.3) |
| `c` | constant | 1 server | one deliverable stream (matches the experiment; c is kept as an engine parameter for the M/M/c verification tests) |

Sweeps: `q_days in {45, 60, 90}`, `K_days in {180, 365}` — predeclared
sensitivities, never tuned after seeing held-out results.

Blocking guard: after each run assert `max_t P(Q = K) < 1e-3`; if violated, K is
too small — the run is rerun with the next K formula step and the change is
logged in the run metadata (this replaces silent saturation with an explicit,
recorded decision).

### 3.5 The utilization window and gauge screening (fixes F3's root cause)

Before any inference, each candidate gauge gets a utilization score
`rho[g] = sum(lambda) / sum(mu)` over days with verified flow (both Stage A).
Predeclared admission window: **0.15 <= rho <= 1.20**.

- Below 0.15 the queue is trivially empty (the old pilot sat at 0.02–0.08 — this
  is precisely the regime where a null is guaranteed); above 1.20 it saturates.
  Gauges outside the window are excluded from the confirmatory comparison and
  counted in the screen report.
- The screen report (per candidate gauge: catchment area, command area, mean
  flow, zero fraction, rho under SUP-1/2/3, in/out of window, reason) is a
  paper table. If MOST gauges fall below the window, that is itself a headline
  empirical finding about when deficit-queueing can matter (§8, path B).

Gauge screening criteria (all must hold for inclusion):

1. CAMELS-IND daily flow 1980–2020 (or to record end) with, after the zero audit
   (§3.9), fewer than 10% unusable days inside the analysis window and no
   unhandled interior gap longer than 30 days.
2. Documented catchment area and district mapping (CAMELS-IND attributes).
3. Zero-fraction after classification below 30% unresolved, or the gauge runs
   variant V2 only (§3.9).
4. Spatial dispersion: at most 3 gauges per basin (CAMELS-IND basin id) to limit
   inter-gauge dependence; document overlaps.
5. rho inside the window under at least one supply variant.
6. Target coverage: district SMA (or T1 target of §3.6) available for >= 80% of
   the gauge's analysis months.

Target count: screen **40 candidates**, expect 15–30 usable. The confirmatory
framing (§3.7) is only permitted at gate G4 if usable gauges >= 15; otherwise the
project auto-downgrades to the exploratory framing (protocol change, logged).

### 3.6 Targets and the circularity fix (fixes F5, U4)

The queue adds no stochastic state beyond the rate histories; its only claim to
new information is the demand channel (PET/rain) integrated with supply history
nonlinearly and persistently. Targets are chosen to make that claim testable
rather than circular:

- **T1 (primary, diagnostic):** soil-moisture-anomaly drought threshold
  (SMA <= -15%), **restandardized with training-only (1981–2010) climatology**
  from the raw soil-moisture series of the Drought Intelligence Explorer product.
  If the raw series cannot be accessed (only the externally standardized SMA is
  available), then T1 is replaced as primary by **T1-strict: SPI-3 and SPEI-3
  recomputed from CAMELS-IND/IMD forcings with training-only standardization**,
  and the external SMA becomes an exploratory benchmark with the leakage
  disclosed. The decision is made and logged at gate G4, before unblinding.
- **T2 (secondary, comparability):** the product's published SPI-3/SPEI-3
  benchmarks exactly as before (external climatology — labelled exploratory).
- **T3 (optional, if obtainable):** district irrigation-deficit / crop-stress
  records (CGWB, agriculture department) — the construct closest to the queue.
  Best-effort; absence is disclosed, not substituted.

Model families fitted per gauge (logistic, L2 = 1, calendar-month dummies,
features standardized on training years, train 1981–2010, test 2011–2020 or to
record end):

`climatology | spi3 | spei3 | ssi3 | queue | ssi3+queue | spei3+queue | ssi3+spei3+queue`

- Primary contrast (diagnostic): `ssi3` vs `ssi3+queue` (continuity with the
  predeclared v1 rule, now with power and clean targets).
- Predeclared secondary contrasts: `spei3` vs `spei3+queue` (the fair
  demand-side competitor — the queue must beat the index that already sees the
  demand channel, or it has no story), and `queue` alone vs all indices.
- `ssi3+spei3+queue` is a descriptive "full information" model, not a contrast.

The prospective endpoint is defined in §3.7 (E2) — same families but with all
predictors lagged to month t-1 predicting the outcome at month t.

### 3.7 Statistical design (fixes F4, U8)

**Endpoints (frozen at gate G4, before any held-out metric is computed):**

- **E1 (confirmatory, diagnostic).** Per gauge g:
  `Delta_g = Brier(ssi3) - Brier(ssi3+queue)` on held-out months at the gauge's
  own q*. Cross-gauge success rule (ALL must hold):
  1. `median(Delta_g) > 0`;
  2. two-level bootstrap 95% CI of the median (resample gauges, then years
     within gauge) excludes 0;
  3. sign test over gauges one-sided p < 0.05 with improvement in >= 60% of
     gauges;
  4. harm bound: no gauge shows `Delta_g < -0.005` driven by calibration
     breakdown (checked with the reliability slope; a breached harm bound forces
     investigation before any claim).
- **E2 (confirmatory, prospective, 1-month lead).** Same rule with all predictors
  taken as of end of month t-1 (ssi3 at t-1, mean and increment of P(Q>=q*) over
  month t-1) predicting the drought outcome at month t. This is the queue's
  genuine test: SSI-3 also persists, but the queue integrates demand and supply
  and its state variable is accumulated, not differenced.
- **Secondaries (reported, never upgraded post hoc):** Delta AUC, Delta log loss,
  reliability slope/intercept, event detection timing (median detection lag),
  recovery-time indicator utility, queue-alone vs indices.

**Power protocol (before unblinding).** Using TRAINING-period fitted models only:

1. Estimate per-gauge variance of `Delta_g` via year-block bootstrap on training
   months (out-of-sample-ish via expanding-window refits if feasible; disclose).
2. Simulate the cross-gauge median under H0 (shift Delta_g to zero mean) and
   under H1 (add assumed uplift; run uplift grid `AUC +0.02/+0.05/+0.08`) for
   N = 10, 15, 20, 30 gauges; report minimal detectable effect at alpha = 0.05,
   power = 0.80.
3. Gate G4 passes only if the MDE at the achievable N is <= the assumed uplift
   for at least the +0.05 grid point; otherwise downgrade to exploratory framing
   (logged protocol amendment) — the paper then says "no evidence" with the power
   analysis shown, not "no effect".

**Multiplicity.** The two confirmatory endpoints are protected; everything else
is labelled exploratory in every table; ALL sensitivity results are reported
regardless of direction (no selective reporting — this rule is inherited from the
v1 culture and must survive).

**Event definition.** Drought event = >= 2 consecutive target months below
threshold (monthly isolated hits are also scored but reported separately).
Event-month counts per gauge and split are part of the power table.

### 3.9 Zero-flow semantics: audit then variants (fixes F2)

**Audit (stage S2, mandatory, per gauge):**

1. Join CAMELS-IND daily flow with an independent record for the same station or
   same district: CWC daily/monthly, India-WRIS, or state board series. Where a
   station match is impossible, use basin-level CWC records as a proxy and mark
   the match grade (exact / proxy / unavailable).
2. Classify every zero day: `real-zero` (independent record also ~0),
   `artifact` (independent record > 0), `unknown` (independent record missing).
3. Output: per-gauge zero-classification table + a monthly artifact-rate series.
   Gauges with > 30% `unknown` zeros are excluded unless variant V2 covers them.

**Treatment variants (predeclared, all run end to end):**

- **V0 as-recorded:** zeros are true zero supply (v1 behaviour; kept only to
  quantify the artifact's impact).
- **V1 zeros-as-missing:** artifact and unknown zero days are treated as missing:
  gaps <= 7 days carry the queue state forward with NO arrival and NO service
  that day (state pause — explicit, flagged); longer gaps exclude the month from
  indicator aggregation and model fitting (the month's features are NA, never
  silently filled). Rainfall/PET are never interpolated across excluded months.
- **V2 verified-flow-only:** restrict the whole analysis window to months whose
  days are >= 90% verified positive-or-true-zero per the audit; the record may
  become discontinuous, and splits are defined on the retained months (the
  bootstrap resamples retained years).

The primary analysis uses V1 (the physically honest default); V0 exists to
demonstrate the artifact's effect on the old result; V2 is the robustness bound.

### 3.10 Queue engine specification (R, replaces all Python)

One file, `R/00_utils/queue_engine.R`, plain R, no S4/R6, no C deps. The model is
the finite-capacity birth-death CTMC with reneging and state-dependent service —
mathematically identical to the verified v1 engine; the rebuild is about clean
units and guardrails, not new math.

```r
# Core identities (state n = 0..K)
birth_n  <- function(n, lam, cfg) ifelse(n < cfg$K, lam, 0)
death_n  <- function(n, mu, cfg) {
  serve <- pmin(n, cfg$c) * mu * ifelse(n >= cfg$theta, cfg$alpha, 1)
  serve + n * cfg$eta
}
stationary <- function(lam, mu, cfg) {          # exact product form
  d <- death_n(0:cfg$K, mu, cfg); b <- birth_n(0:cfg$K, lam, cfg)
  pi <- numeric(cfg$K + 1); pi[1] <- 1
  for (i in 2:(cfg$K + 1)) pi[i] <- pi[i-1] * b[i-1] / d[i]
  pi / sum(pi)
}
```

- **Transient:** RK4 on `dp/dt = p A(t)` with daily piecewise-constant rates.
  Adaptive step: `dt = min(0.1, 0.1 / (lam + death_max))` where
  `death_max = c*mu*alpha + K*eta`. After EVERY step renormalize `p <- p/sum(p)`
  and assert `abs(sum(p) - 1) < 1e-8`; assert `all(p >= 0)` after clipping at 0.
  Warm-up: initialize empty at 1979-01-01, discard 1980 (as v1).
- **DES cross-check:** thinning with bound
  `Gamma = lam_max + c*mu_max*alpha + K*eta`; jump-epoch bias corrected by
  dwell-time weighting for time averages. Used only inside the verification
  battery and one pilot spot-check per gauge (cheap sanity, not shipped results).
- **First passage:** mean time from state q* to state 0 via the
  negative-generator solve on states 1..K (identical construction to v1; a
  verification test compares it against simulated hitting times).
- **Indicators and ledger (daily):** `E_Q = sum(n*p)`;
  `p_ge(q*) = sum(p[q*..K])`; served = integral of service flux; abandoned =
  integral of (reneging + blocked) fluxes; **conservation check per day**:
  `total_arrivals = served + abandoned + Delta_backlog` within `1e-6` — a failed
  check STOPS the pipeline (this ledger identity is the project's signature
  honesty device; keep it).
- **Units:** the engine takes rates in claims/day ONLY; conversion happens in
  `units.R` once, upstream, with the per-gauge claim volume. The engine never
  sees m^3 or areas (this architectural wall is what makes an F1 recurrence
  impossible).
- **Output schema (daily, per gauge, per variant):** date, lambda, mu (claims/day),
  E_Q, P(Q>=q*), P(Q>=theta), P(Q=K), served, reneged, blocked, rho_day, flags
  (imputed/paused/excluded). Monthly aggregation: means over COMPLETE months
  only (a month missing any retained day is excluded with a flag), plus
  month-start state for the prospective lag.

Performance note: K <= 80 states, ~15,000 days, ~30 gauges x ~20 runs — RK4 in
plain R with vectorized state vectors is seconds per run; no compiled code needed
("linear R" constraint respected). If runtime ever matters, memoize the
per-day-step matrices; do NOT introduce Rcpp.

### 3.11 Rate-estimator module (bounded, optional, verified)

The v1 project's novelty component 3 ("non-stationary rates estimated from
hydroclimatic covariates") is preserved with a deliberately small module:

- `est_lambda`: log-linear GLM of need_mm on (PET0, P, month harmonics) fitted on
  training years; `est_mu`: log-linear GLM of observed flow on (season, upstream
  rain, lagged flow). Rates = predictions x factor offsets to preserve the mean.
- Verification: fit on synthetic data generated from KNOWN lambda(t), mu(t) with

## 5. R Markdown execution architecture

Every numbered notebook follows the same contract:

1. **Header:** stage number, purpose, inputs (files + schema), outputs (files),
   parameters used (from config.R), seed.
2. **Load:** reads only files produced by earlier stages or the raw data roots;
   refuses to run if an upstream output is missing (explicit stop with a message
   naming the stage to run first).
3. **Compute:** linear, commented, section-per-substep; helper calls into
   `00_utils`; no hidden state between notebooks (all exchange via files).
4. **Assert:** every notebook ends with an assertion block — schema checks, unit
   checks (via units.R), conservation checks, no-NaN checks on required columns,
   row-count sanity vs the inventory — any failure stops rendering.
5. **Record:** writes a sidecar `.json` (script, git hash via `system2("git", ...)`,
   parameters, seed, `sessionInfo()`, run timestamp) next to every output.

The narrative text in each notebook is written as if it will become the paper's
methods section: what is done, why, with which assumption — this is how the v2
rebuild also fixes the documentation drift (F7): the notebooks ARE the
documentation, and they cannot silently disagree with the code.

  - **Path B — honest null:** rules fail but the test was powered and clean →
    the paper is the predeclared evaluation + utilization diagnosis: rho
    distribution across basins, the regime table, what demand/supply regimes

## Appendix C — Formula quick reference

- need_mm(t) = max(Kc(doy)*PET0(t) - phi*P(t), 0)  [mm/day over A_cmd]
- lambda(t) = need_mm(t) / d  [claims/day, d = 20 mm]
- S_raw(t) = Q(t)*86400*s_firm  [m^3/day; Q in m^3/s, 86,400 s/day]
- S_mm(t) = S_raw(t) / A_cmd[g] * 1000  [mm/day over A_cmd]
- mu(t) = min(S_mm(t), cap_mm) / d  [claims/day]
- rho[g] = sum(lambda) / sum(mu)  [utilization; window 0.15–1.20]
- q*[g] = ceiling(q_days * lam_bar[g]); K[g] = min(80, max(25, ceiling(K_days * lam_bar[g])))
- V_claim[g] = d/1000 * A_cmd[g]  [m^3; used by BOTH fluxes, nowhere else]
- ledger: arrivals = served + abandoned + Delta_backlog  [per day, < 1e-6]
